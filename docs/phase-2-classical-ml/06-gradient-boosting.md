# Урок 06 — Gradient Boosting

## Що це

**Gradient Boosting** — ансамбль дерев, як і Random Forest, але побудований інакше. RF будує 200 дерев **паралельно й незалежно**, потім голосує. Boosting будує дерева **послідовно**: кожне наступне дерево вчиться не на оригінальних відповідях, а на **залишку помилки** (residual) — тому, що попередні дерева разом ще не вгадали.

Слово «градієнт» тут не декоративне: це той самий градієнтний спуск (Фаза 1, Урок 05, `w -= lr * grad`), тільки крок робиться не над одним числом `w`, а над цілою функцією прогнозу — «крок у бік зменшення loss» реалізується як **нове дерево, натреноване на залишку**.

## Для чого

Gradient Boosting (у вигляді XGBoost/LightGBM/CatBoost) — один із найуживаніших інструментів на табличних даних у продакшні й на Kaggle, часто виграє в моделей на основі нейромереж для структурованих даних. На відміну від класичної нейромережі, добре працює «з коробки», без тонни даних і GPU.

### Loss function — що мінімізує boosting

Перед тим, як розбирати сам boosting, треба розуміти, **що саме** він мінімізує. Для класифікації це не MSE (Уроки 04-05), а **cross-entropy (log-loss)**:

```
loss = -( y·log(p) + (1-y)·log(1-p) )
```

де `y` — правда (0/1), `p` — ймовірність, яку дає модель (`.predict_proba()`).

Порахувавши руками на трьох прикладах (`y=1`, різні `p`):

| y | p | loss |
|---|---|---|
| 1 | 0.99 (впевнена, права) | **0.01** |
| 1 | 0.50 (не впевнена) | **0.693** |
| 1 | 0.01 (впевнена, **не права**) | **4.605** |

Ключовий інсайт: однаковий крок у ймовірності (`p` падає на 0.49 в обох переходах: 0.99→0.50 і 0.50→0.01) дає **різний** приріст loss (0.683 проти 3.912). Функція `-log(p)` не лінійна — вона майже пласка біля `p=1` і різко задирається вгору біля `p=0`. Тому **cross-entropy жорстко карає самовпевнену помилку**, набагато сильніше за чесну невпевненість.

### Механіка: дерево вчиться на залишку

```python
from sklearn.ensemble import GradientBoostingClassifier

gb = GradientBoostingClassifier()  # n_estimators=100, max_depth=3, learning_rate=0.1 за замовч.
gb.fit(X_train_prepared, y_train)
```

Уяви одного клієнта, `y=1` (пішов):
- дерево №1 передбачає `0.7` → залишок `1 - 0.7 = 0.3`
- дерево №2 вчиться **на цьому залишку 0.3**, трохи його зменшує → залишок `0.1`
- дерево №3 вчиться на залишку після дерев 1+2 → залишок `0.03`
- і так далі — кожне наступне дерево ганяється за все дрібнішим шматком того, чого попередні не вловили.

### Порівняння з попередніми моделями

| | train | test | розрив |
|---|---|---|---|
| deep tree (Урок 05) | 0.999 | 0.732 | 0.27 |
| shallow tree (Урок 05) | 0.796 | 0.780 | 0.02 |
| Random Forest (Урок 05) | 0.999 | 0.789 | 0.21 |
| **Gradient Boosting** | **0.830** | **0.796** | **0.03** |

GB за замовчуванням обережний (`max_depth=3`, `learning_rate=0.1` — кожне дерево робить маленький крок) — дав **найкращий test** серед усіх чотирьох, при цьому з найменшим розривом train↔test.

### Небезпека великого `n_estimators` — і чому вона різна для RF і GB

Якщо boosting дати **дуже багато** дерев (наприклад, 2000 замість 100), кожне наступне продовжує дожимати залишок на **train**. Залишок з кожним деревом падає ближче до нуля — модель поступово завчує train ідеально, **включно з шумом**. Це та сама картина, що й глибоке дерево на самому початку Уроку 05 (train 0.999 → test 0.732) — **overfitting**.

RF цього уникає, бо його 200 дерев **незалежні** — жодне не намагається «виправити» те, що лишили інші, вони просто голосують. Додавання ще дерев тільки стабілізує прогноз, не заглиблює підгонку під шум.

> **RF додає дерева паралельно й незалежно — стійкий до їхньої кількості. Boosting додає дерева послідовно, кожне ганяється за залишком попередніх — забагато дерев = overfitting, як в одного глибокого дерева.**

### Feature importances — нова пастка: `max_features`

```python
importances = pd.Series(
    gb_pipe.named_steps["gradient_boosting"].feature_importances_,
    index=gb_pipe.named_steps["preprocessor"].get_feature_names_out(),
).sort_values(ascending=False)
```

Топ фіч у GB несподівано інший за формою, ніж у RF:

| фіча | RF | GB |
|---|---|---|
| Contract_Month-to-month | 0.053 | **0.393** |
| TotalCharges | 0.157 | 0.104 |
| tenure | 0.144 | 0.130 |
| MonthlyCharges | 0.135 | 0.080 |

Одна фіча (`Contract_Month-to-month`) забирає майже **40%** усієї важливості в GB — набагато більше, ніж будь-що в RF. Причина — різні дефолти `max_features`:

```python
GradientBoostingClassifier().max_features  # None  → бачить УСІ фічі на кожному спліті
RandomForestClassifier().max_features      # 'sqrt' → бачить лише √n_features (випадкова підмножина)
```

RF на кожному спліті випадково показує дереву лише ~5 із 19 фіч. `Contract_Month-to-month` (об'єктивно найсильніший роздільник) фізично **присутня** в списку кандидатів лише на ~26% сплітів (5/19). На решті 74% дерево її навіть не бачить і мусить обирати з гірших варіантів — тому за весь ліс вона накопичує менше сумарної заслуги.

GB бачить усі 19 фіч на **кожному** спліті — і оскільки ця фіча справді найкраща, її обирають найчастіше, заслуга не розсіюється.

> **`feature_importances_` залежить не тільки від того, наскільки фіча об'єктивно хороша, а й від того, скільки разів алгоритм дав їй шанс бути обраною.** Пастка з корельованими фічами (Урок 05, `tenure`/`TotalCharges`) при цьому нікуди не зникає — вона присутня в GB так само.

## Gotchas

- **`n_estimators` у boosting — не «чим більше, тим краще»**, на відміну від RF. Занадто багато дерев = overfitting. Потрібен tuning (`learning_rate` + `n_estimators` разом, або `n_iter_no_change` для ранньої зупинки).
- **`pd.to_numeric(...)` — функція модуля `pandas`, не метод DataFrame.** `df.to_numeric(...)` впаде з `AttributeError`. Правильно: `pd.to_numeric(df["col"], errors="coerce")`.
- **`select_dtypes(include=..., exclude=...)`** — параметри в однині, не `includes`/`excludes`.
- **`.predict()` очікує фічі (`X`), не мітки (`y`).** Легко переплутати `X_test`/`y_test`, коли береш `.iloc[:30]` для семпла — traceback (`X does not contain any features, but ColumnTransformer is expecting N features`) вкаже на це не одразу очевидним чином.
- **`max_features` — різний дефолт у RF і GB.** Не можна вважати, що обидва ансамблі трактують важливість фіч однаково — перевіряти дефолти явно (`model.max_features`), не покладатись на пам'ять.
