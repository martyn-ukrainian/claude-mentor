# Урок 08 — Overfitting, регуляризація (L1/L2), крос-валідація

## Що це

**Регуляризація** — техніка, що штучно «карає» модель за завеликі коефіцієнти під час навчання, щоб вона не підганялась під шум у train-даних. **Крос-валідація (K-Fold)** — спосіб оцінити модель надійніше, ніж одним `train_test_split`: дані діляться на K частин, модель навчається й перевіряється K разів на різних частинах, результати усереднюються.

## Для чого

Overfitting уже бачили практично (deep tree, Gradient Boosting з забагато дерев) — цей урок дає формальний інструментарій боротьби з ним і формальний спосіб довіряти (чи не довіряти) числу, яке видала модель.

## Розбір

Той самий Telco Churn, той самий фундамент з попередніх уроків.

### Регуляризація: L1 vs L2

У sklearn `LogisticRegression` регуляризація задається параметром `C` — **обернена** сила регуляризації:
- **Великий `C`** (100) → слабка регуляризація → коефіцієнти майже вільні.
- **Малий `C`** (0.01) → сильна регуляризація → коефіцієнти сильно стиснуті до нуля.

Вид регуляризації — параметр `l1_ratio` (у sklearn ≥1.7, замінив застарілий `penalty`):
- `l1_ratio=0` → чиста **L2** (Ridge) — коефіцієнти зменшуються плавно, рідко рівно нуль.
- `l1_ratio=1` → чиста **L1** (Lasso) — деякі коефіцієнти можуть стати **рівно 0**.

```python
LogisticRegression(l1_ratio=1, solver="liblinear", C=100)
```

**Геометрична причина, чому L1 занулює, а L2 — ні:** L1-обмеження має форму ромба з гострими кутами навколо нуля; оптимальна точка часто потрапляє рівно в кут — а кут це вісь, де один із коефіцієнтів точно нуль. L2-обмеження — коло, без гострих кутів, тому мінімум рідко припадає точно на вісь.

### L1 і мультиколінеарність — не така передбачувана, як здається

`tenure`, `MonthlyCharges`, `TotalCharges` скорельовані (`TotalCharges ≈ tenure × MonthlyCharges`, corr 0.83). Перевірка на реальних числах, різні `C`:

| C | tenure | MonthlyCharges | TotalCharges |
|---|---|---|---|
| 100 | -1.411 | -2.119 | 0.705 |
| 1 | -1.352 | **0.0** | 0.64 |
| 0.1 | -0.948 | 0.858 | 0.142 |
| 0.01 | -0.92 | 0.705 | **0.0** |

При `C=1` зникає `MonthlyCharges`. При `C=0.1` він **повертається**. Тільки при `C=0.01` зникає `TotalCharges`, а `MonthlyCharges` знову живий. **Не монотонна історія** — L1 при сильній кореляції жертвує **кимось одним** із групи, щоб зекономити на штрафі, але **хто саме** — залежить від сили регуляризації і не завжди легко передбачити наперед. Можна впевнено сказати лише, що хтось один із корельованої групи буде принесений у жертву.

### Underfitting — симетричний партнер overfitting

Порівняння train/test для трьох `C`:

| C | train | test |
|---|---|---|
| 100 | 0.8053 | 0.7974 |
| 1 | 0.8041 | **0.8017** |
| 0.01 | **0.8014** ↓ | **0.7861** ↓ |

Діагностична різниця:
- **Overfitting** (deep tree, Урок 05): train **дуже високий**, test **набагато нижчий** — модель завчила шум.
- **Underfitting** (`C=0.01`): train **теж просів** — регуляризація настільки стиснула коефіцієнти, що модель не може використати весь корисний сигнал навіть на train.

> Overfitting: train відмінний, test поганий. Underfitting: train теж посередній — модель занадто обмежена.

Занулені коефіцієнти підтверджують механізм:

| C | занулених коеф. (з 45) |
|---|---|
| 100 | 0 |
| 1 | 13-15 |
| 0.01 | 33 |

### Крос-валідація: чому одного спліту недостатньо

Емпірична демонстрація — той самий `C=1`, різні `random_state`:

| random_state | test acc |
|---|---|
| 42 | 0.8017 |
| 1 | 0.7960 |
| 7 | 0.8081 |
| 99 | 0.7946 |
| 2024 | 0.8017 |

Розкид **1.35 пункта** — лише через те, які рядки випадково потрапили в test. Майже стільки ж, скільки різниця між різними `C`! Один спліт може дати оманливий висновок.

```python
from sklearn.model_selection import cross_val_score

cv_scores = cross_val_score(pipe, X, y, cv=5, scoring="accuracy")
cv_scores.mean(), cv_scores.std()
```

**Ключове:** сюди даємо **весь** `X`/`y`, не `X_train`/`X_test` — `cross_val_score` сам ділить дані на 5 фолдів усередині.

### Головний твіст уроку — CV змінює висновок, зроблений на одному спліті

CV для всіх трьох `C`:

| C | mean CV | std |
|---|---|---|
| 100 | 0.8043 | 0.0091 |
| 1 | 0.8038 | 0.0067 |
| 0.01 | **0.7965** | 0.0064 |

На одному спліті здавалось, що `C=1` — «sweet spot» (0.8017 проти 0.7974 у `C=100`). Але за CV різниця `mean` між `C=100` і `C=1` — лише **0.0005**, набагато менша за `std` (~0.007-0.009). **Статистично невідрізнимо.** Той попередній висновок був частково артефактом конкретного `random_state=42`.

Що CV **підтверджує** стабільно: `C=0.01` (0.7965) — реальне падіння, більше за std. Сильна регуляризація справді шкодить.

Бонус: `std` теж потроху падає з посиленням регуляризації (0.0091 → 0.0067 → 0.0064) — логічно, регуляризація знижує variance, моделі стають стабільнішими між фолдами.

> **Правило порівняння:** якщо різниця в `mean` між двома варіантами менша за `std` — це статистично невідрізнимо, не робимо висновок на основі такої різниці.

## Gotchas

- **`penalty` deprecated у sklearn ≥1.8** (перевірено на встановленій версії 1.9.0) — новий спосіб `l1_ratio` (0=L2, 1=L1, проміжне значення=Elastic Net). Перевіряти актуальний API через docstring/офіційні docs, а не покладатись на пам'ять — версії sklearn рухаються швидко.
- **`C` — обернена сила регуляризації.** Легко переплутати: великий `C` = слабка регуляризація (протилежно інтуїції «більше число = більше обмежень»).
- **Підрахунок занулених коефіцієнтів вимагає порівняння, не просто `.sum()`.** `model.coef_[0].sum()` підсумовує значення (може дати від'ємне дробове число). Правильно: `(model.coef_[0] == 0).sum()` — спершу порівняння дає boolean-масив, потім `.sum()` рахує `True`.
- **`cross_val_score` бере весь `X`/`y`**, не заздалегідь розділені `X_train`/`X_test` — він сам виконує розбиття на фолди всередині.
- **Copy-paste bug у циклі:** легко жорстко «прилипнути» до однієї змінної замість циклової (`cross_val_score(pipe_2, ...)` замість `cross_val_score(pipe, ...)`) — симптом: підозріло ідентичні результати для різних ітерацій. Якщо два різні експерименти дають однакові числа до восьмого знака — це майже завжди бага, не збіг.
- **Sweet spot з одного спліту може бути шумом.** Перед тим, як робити висновок про кращий гіперпараметр на основі одного `train_test_split`, порівнювати `mean`/`std` через крос-валідацію.
