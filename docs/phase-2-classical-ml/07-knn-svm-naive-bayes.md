# Урок 07 — KNN, SVM, Naive Bayes

## Що це

Три різні «філософії» класифікації, кожна з іншим підходом до прогнозу:

- **KNN (K-Nearest Neighbors)** — «подивись на К найближчих сусідів, візьми більшість». Немає навчання у звичному сенсі — модель це просто збережені точки.
- **SVM (Support Vector Machine)** — шукає межу, що максимально розділяє класи з найбільшим запасом (margin).
- **Naive Bayes** — імовірнісна модель, рахує `P(клас | фічі)` через теорему Байєса, припускаючи що фічі незалежні одна від одної («naive» — наївне припущення).

## Для чого

KNN/SVM — класика, менш вживана в проді за дерева/бустинг сьогодні, але корисна для розуміння різних підходів до задачі та як baseline. Naive Bayes — швидкий, дешевий baseline, особливо для тексту (спам-фільтри, тональність) де є природні бінарні/лічильникові фічі.

## Розбір

Той самий Telco Churn, той самий фундамент (`ColumnTransformer` + `train_test_split(stratify=y)`).

### Scaling — тепер обов'язковий, не факультативний

На відміну від дерев (Урок 05, де scaling був «нешкідливим, але зайвим»), для KNN і SVM він **необхідний**. Причина — обидва алгоритми рахують **відстань або добуток**, що змішує всі фічі в одну формулу:

```
distance = √( (tenure_A - tenure_B)² + (TotalCharges_A - TotalCharges_B)² )
```

Візьмемо двох клієнтів: A (`tenure=2, TotalCharges=100`), B (`tenure=70, TotalCharges=110`):

```
distance = √( (2-70)² + (100-110)² ) = √( 4624 + 100 )
```

`4624` проти `100` — `tenure` домінує в 46 разів, хоча жодних об'єктивних підстав вважати різницю в місяцях важливішою за різницю в гривнях немає. Це чиста випадковість одиниць виміру. Після `StandardScaler` обидві фічі мають приблизно однаковий розмах (`mean=0, std=1`), тому жодна не домінує лише через одиниці.

> **Scaling потрібен, коли алгоритм змішує фічі в одну формулу** (відстань — KNN, SVM/K-means; зважена сума — лінійна/логістична регресія). Дерева розглядають кожну фічу окремо через поріг — тому байдужі до масштабу.

### Порівняння моделей

| модель | train | test |
|---|---|---|
| KNN | 0.833 | 0.760 |
| SVM | 0.820 | **0.792** |
| GaussianNB (усі фічі) | 0.701 | 0.682 |

Для довідки з попередніх уроків: GB 0.796 (найкращий загалом), RF 0.789, shallow tree 0.780. SVM впевнено на другому місці серед усього курсу.

### Теорема Байєса — на реальних числах

Naive Bayes рахує `P(Churn | фічі)`, але напряму це важко виміряти для комбінації багатьох фіч. Теорема Байєса дозволяє порахувати це через величини, які легше виміряти:

```
P(Churn | Contract) = P(Contract | Churn) × P(Churn) / P(Contract)
```

На реальних даних Telco:

| величина | значення | що означає |
|---|---|---|
| `P(Churn=Yes)` | 0.265 | базова частка churn (**prior** — до нового доказу) |
| `P(Contract=Month-to-month)` | 0.550 | скільки клієнтів взагалі на місячному контракті |
| `P(Contract=Month-to-month \| Churn=Yes)` | 0.886 | серед тих, хто пішов, скільки мали місячний контракт (**likelihood**) |

```
P(Churn=Yes | Contract=Month-to-month) = (0.886 × 0.265) / 0.550 = 0.427
```

Перевірено напряму з даних (проста частка) — теж **0.427**. Байєс не наближення, а точний результат через інший шлях рахування. До того, як дізнався тип контракту — найкраща оцінка ризику 26.5% (**prior**). Дізнавшись «Month-to-month» — оновлюєш до 42.7% (**posterior**).

**Де тут «naive»:** повна версія мала б рахувати `P(Contract, InternetService, tenure, ... | Churn)` — спільну ймовірність усіх комбінацій одразу, що вимагає astronomічно багато даних. Naive Bayes спрощує, припускаючи незалежність:

```
P(Contract, InternetService, tenure, ... | Churn) ≈ P(Contract|Churn) × P(InternetService|Churn) × P(tenure|Churn) × ...
```

### Naive Bayes — чотири експерименти

| варіант | train | test |
|---|---|---|
| `GaussianNB` (усі фічі) | 0.701 | 0.682 |
| `GaussianNB` (тільки numeric) | 0.775 | **0.778** |
| `BernoulliNB` (усі фічі) | 0.729 | 0.709 |
| `VotingClassifier` (GNB-numeric + BNB-categorical) | 0.749 | 0.728 |

**1. `GaussianNB` на всіх фічах — найгірший результат, дві причини:**
- **Незалежність фіч vs кореляція.** `tenure` і `TotalCharges` скорельовані на 0.83 (`TotalCharges ≈ MonthlyCharges × tenure`). NB перемножує `P(tenure|churn) × P(TotalCharges|churn)` як два незалежні докази, хоча це один факт, порахований двічі.
- **Розподіл vs тип даних.** `GaussianNB` очікує, що кожна фіча в межах класу розподілена нормально (як зріст людей). Але після `OneHotEncoder` — 30+ колонок 0/1, зовсім не гаусів розподіл.

**2. Прибрали OneHot, лишили тільки числові — test підскочив із 0.682 до 0.778.** Підтверджує, що причина «розподіл vs тип даних» домінує над «незалежність фіч».

**3. `BernoulliNB` на всіх фічах — 0.709, посередині.** `BernoulliNB` очікує бінарні (0/1) дані — ідеально підходить для OneHot-колонок. Але для числових фіч він тихо **бінаризує** їх за порогом `binarize=0.0` (перевірено: `BernoulliNB().binarize == 0.0`). Після `StandardScaler` (mean=0) це означає «вище/нижче середнього» — `tenure` (0-72 місяці) звівся до одного біта, втративши майже всю інформацію.

**4. `VotingClassifier` — «правильно розділені» моделі об'єднані — і результат гірший за найкращий окремий компонент:**

```python
from sklearn.ensemble import VotingClassifier

pipe_gnb_numeric = Pipeline([
    ("preprocessor", ColumnTransformer([("number", StandardScaler(), numeric_cols)])),
    ("model", GaussianNB())
])
pipe_bnb_categorical = Pipeline([
    ("preprocessor", ColumnTransformer([("category", OneHotEncoder(), categorical_cols)])),
    ("model", BernoulliNB())
])

combined = VotingClassifier(
    estimators=[("gnb", pipe_gnb_numeric), ("bnb", pipe_bnb_categorical)],
    voting="soft",
)
```

Перевірено компоненти окремо: `GaussianNB(numeric)` сам по собі = 0.778, `BernoulliNB(categorical)` сам по собі = 0.702. `VotingClassifier` дав їм **рівну вагу** (50/50) — сильний «свідок» розбавився слабшим, підсумок (0.728) впав між ними, гірше за найкращий компонент окремо.

**Порівняння з Random Forest:** там 200 «голосів»-дерев приблизно **рівні за силою** (той самий алгоритм, схожі підвибірки) — усереднення допомагає, бо немає систематично слабшого учасника. У `VotingClassifier` вище — два компоненти **нерівні** (0.778 проти 0.702), і рівна вага одного з них шкодить сильнішому.

> **Усереднення допомагає, тільки коли учасники голосування приблизно рівні за силою.** Виправлення — `weights=[2, 1]` (дати сильнішій моделі більшу вагу) або перевіряти компоненти окремо перед об'єднанням.

## Gotchas

- **`ColumnTransformer` не може «розділити» фінальну модель по колонках.** Він — transformer (fit+transform, повертає одну матрицю), а `GaussianNB`/`BernoulliNB` — estimator-и (fit+predict). Pipeline — лінійний ланцюжок з **одним** фінальним кроком. Щоб навчити різні моделі на різних підмножинах колонок і об'єднати прогнози — потрібен інший інструмент, `VotingClassifier`/`StackingClassifier` (рівень над Pipeline, об'єднує вже готові прогнози, не трансформує фічі).
- **`BernoulliNB(binarize=0.0)`** — тихо бінаризує будь-які неперестворені неперервні фічі за порогом 0. Не кидає помилку, просто губить інформацію. Перевіряти дефолтні параметри моделі (`model.binarize`), а не покладатись на здогад.
- **`VotingClassifier(voting="soft")` за замовчуванням дає рівну вагу всім компонентам.** Якщо компоненти суттєво різні за силою — результат може бути гірший за найкращий окремий компонент. Перевіряти якість кожного компонента окремо перед об'єднанням.
- **Naive Bayes — не одна модель, а сімейство** з різними припущеннями про розподіл: `GaussianNB` для неперервних, `BernoulliNB` для бінарних, `CategoricalNB` для категоріальних. Застосувати не той варіант до не того типу даних — типова помилка новачка.
