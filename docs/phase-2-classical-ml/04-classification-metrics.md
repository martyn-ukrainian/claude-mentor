# Метрики класифікації: confusion matrix, precision/recall/F1, ROC-AUC

## Що це

Набір інструментів, які показують, **наскільки добре** модель класифікації справляється — окремо для кожного класу, а не одним розмитим числом (accuracy). Включає confusion matrix, precision, recall, F1 та ROC-AUC.

## Для чого

В Уроці 03 ми побачили, що модель з accuracy `80.4%` не набагато краща за "ліниву" модель (`73.4%`), яка взагалі ігнорує клієнтів, що йдуть. Але accuracy не показує **чому** — потрібні метрики, які дивляться саме на клас, що цікавить бізнес (churn=1), а не розмивають його у загальній цифрі.

## Розбір

### Confusion matrix — фундамент

Таблиця 2×2, що розкладає прогнози на 4 категорії (у термінах churn-бізнесу):

|                        | Модель каже "піде" | Модель каже "не піде" |
|------------------------|---------------------|-------------------------|
| **Реально пішов**      | TP — зловили вчасно | FN — прогледіли, втратили клієнта |
| **Реально не пішов**   | FP — дарма витратили бюджет | TN — правильно проігнорували |

```python
from sklearn.metrics import confusion_matrix
cm = confusion_matrix(y_test, y_pred)
# [[TN, FP],
#  [FN, TP]]
```

**FN дорожчий за FP** для retention-задачі — пропущений клієнт означає втрачену виручку на весь lifetime value, а дарма запропонована знижка — це лише маркетинговий бюджет.

### Precision і Recall — різний знаменник

```
precision = TP / (TP + FP)   # з усього, що модель НАЗВАЛА "piде"
recall    = TP / (TP + FN)   # з усіх, хто РЕАЛЬНО пішов
```

Приклад, який показує різницю: модель назвала 100 клієнтів "піде", з них 30 справді пішли → `precision = 30/100 = 30%`. Але реально пішло 200 клієнтів, з них модель зловила ті самі 30 → `recall = 30/200 = 15%`. Той самий `TP=30`, різний знаменник — різне число.

**Ручний приклад (confusion matrix для 1000 клієнтів: `TP=80, FP=20, FN=40, TN=860`):**
- `accuracy = (TP+TN)/1000 = 940/1000 = 94%`
- `precision = 80/(80+20) = 80%`
- `recall = 80/(80+40) ≈ 66.7%`

**Чому 94% accuracy тут оманлива:** 40 пропущених клієнтів (33% реальних churners, `recall` показує це чесно) — це лише 4% від загальних 1000 рядків. Accuracy **розчиняє** помилку на міноритарному класі у величезній кількості правильних TN, тому високий % не означає, що модель добре ловить саме клас, який цікавить бізнес.

### F1 — гармонійне, не арифметичне середнє

```
F1 = 2 * (precision * recall) / (precision + recall)
```

Арифметичне середнє **заколисує**: модель з `precision=1.0, recall=0.01` (ловить 1 клієнта зі 100, зате завжди влучає) дає арифметичне `(1.0+0.01)/2 = 0.505` — виглядає як "так собі, 50/50". Але модель **пропускає 99%** реальних випадків — майже марна. F1 для цього ж прикладу: `2*(1.0*0.01)/(1.0+0.01) ≈ 0.02` — чесно показує, що модель марна.

**Розрив між арифметичним і F1 максимальний, коли precision і recall сильно відрізняються одне від одного** (одне близько до 1, інше близько до 0) — не коли обидва просто малі. Наприклад, `(0.09, 0.01)` дає меншу різницю, ніж `(0.9, 0.1)`, бо це просто пропорційно зменшена версія тієї самої пари — драма залежить від **асиметрії**, не від абсолютної величини.

### ROC-крива і AUC

Для кожного можливого порогу рахуємо дві точки:
- **TPR** (= recall) — вісь Y.
- **FPR = FP/(FP+TN)** — вісь X.

```python
from sklearn.metrics import roc_curve, roc_auc_score
fpr, tpr, thresholds = roc_curve(y_test, y_proba)
roc_auc_score(y_test, y_proba)
```

**AUC = 0.5** — модель не краща за монетку: випадкове вгадування дає `TPR≈FPR` на кожному порозі, крива йде по діагоналі, площа під діагоналлю рівно `0.5`. **AUC = 1.0** — ідеальна модель. Перевірка на власних даних: реальна модель дала `AUC≈0.836`, `np.random.rand()` замість реальних ймовірностей дав `AUC≈0.49-0.50` (близько до 0.5, але не рівно — це статистичне очікування, не аналітична гарантія).

**Gotcha:** `roc_auc_score`/`roc_curve` приймають **ймовірності** (`predict_proba(...)[:, 1]`), не бінарні `.predict()` — інакше крива вироджується у дві точки.

### Threshold tuning — свідомий вибір порогу

`.predict()` всередині використовує поріг `0.5` за замовчуванням — це просто `(y_proba >= 0.5).astype(int)`. Але `0.5` — довільний дефолт, не частина того, що модель "вивчила". Це окреме правило прийняття рішення, накладене **зверху** на вже готові ймовірності.

```python
from sklearn.metrics import precision_score, recall_score

for threshold in [0.2, 0.3, 0.5, 0.7, 0.8]:
    y_pred_t = (y_proba >= threshold).astype(int)
    p = precision_score(y_test, y_pred_t)
    r = recall_score(y_test, y_pred_t)
    print(f"threshold={threshold}: precision={p:.3f}, recall={r:.3f}")
```

Результат на Telco Churn:

| threshold | precision | recall |
|-----------|-----------|--------|
| 0.2 | 0.458 | 0.869 |
| 0.3 | 0.511 | 0.759 |
| 0.5 | 0.648 | 0.572 |
| 0.7 | 0.759 | 0.168 |
| 0.8 | 0.875 | 0.019 |

Нижчий поріг → вищий recall, нижчий precision. Немає "правильного" порогу у вакуумі — є вибір під конкретну бізнес-ціну помилки. Для retention-задачі, де пропустити клієнта дорожче за дарма запропоновану знижку, розумний вибір — `0.3` (recall `75.9%` ціною precision `51.1%`), а не крайні `0.2` чи `0.8`.

**AUC ≠ threshold.** AUC — це підсумкова оцінка **по всіх можливих порогах одночасно** (одне фіксоване число для моделі, не змінюється). `threshold` — конкретний параметр, який інженер обирає і міняє руками для одного операційного рішення. Це дві різні речі: AUC оцінює модель загалом, threshold — це рішення про те, як цю модель використовувати на практиці.

## Gotchas

- **Accuracy на незбалансованих класах бреше** — завжди звіряти з baseline (`1 - y.mean()`).
- **Precision і recall мають різні знаменники** — precision дивиться на власні прогнози моделі (`TP+FP`), recall — на реальність (`TP+FN`).
- **F1 ≠ арифметичне середнє** — гармонійне середнє карає дисбаланс, арифметичне його маскує.
- **`roc_auc_score` потребує ймовірностей, не `.predict()`** — передача бінарних класів дає вироджену, малоінформативну криву.
- **AUC — не те саме, що threshold.** AUC — фіксована оцінка моделі по всіх порогах; threshold — окремий вибір для конкретного бізнес-рішення.
- **`Pipeline`/`ColumnTransformer` приймають список `[...]` для `steps`/`transformers`**, не множину `{...}` — легко переплутати дужки, sklearn видасть чітку помилку типу.
