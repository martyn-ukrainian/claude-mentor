# 06 — Перша повна CNN на MNIST: convolution проти Linear на реальних даних

## Що це

Перша повна нейромережа-класифікатор на реальному датасеті (MNIST, 70,000 рукописних цифр 28×28), зібрана з нуля на PyTorch: два згорткові шари з pooling, порівняна напряму з повнозв'язним (`Linear`) baseline на тих самих даних.

## Для чого

До цього уроку CNN (Урок 05) була механікою на іграшкових прикладах — одна згортка, вручну порахований вихід. Тут — перевірка, чи справді weight sharing (Урок 05) дає практичну перевагу на реальних даних, не тільки в теорії. Це прямий, вимірюваний, портфоліо-вартий результат: дві архітектури, однакові дані, однакові умови тренування, порівнюємо параметри й точність.

## Розбір

### Архітектура

```
Conv2d(1→8, kernel=3) → ReLU → MaxPool(2) → Conv2d(8→16, kernel=3) → ReLU → MaxPool(2) → Flatten → Linear(400→10)
```

Shape йде так (вхід `28×28`, 1 канал):

```
(1,28,28) → conv1(k=3) → (8,26,26) → pool(2) → (8,13,13)
          → conv2(k=3) → (16,11,11) → pool(2) → (16,5,5)
          → flatten → (400,) → fc → (10,)
```

`(16,5,5)` після другого pooling — звідси `Linear(400, 10)`: `16*5*5=400`. Кожен крок shape порахований заздалегідь вручну за формулою `(H-K)/S+1` з Уроку 05 — включно з округленням вниз при непарному розмірі для pooling (`11→5`, не `5.5`).

```python
class CNN(nn.Module):
    def __init__(self):
        super().__init__()
        self.conv1 = nn.Conv2d(in_channels=1, out_channels=8, kernel_size=3)
        self.pool = nn.MaxPool2d(2)
        self.conv2 = nn.Conv2d(in_channels=8, out_channels=16, kernel_size=3)
        self.flatten = nn.Flatten()
        self.fc = nn.Linear(400, 10)
        self.relu = torch.relu

    def forward(self, x):
        x = self.conv1(x)
        x = self.relu(x)
        x = self.pool(x)
        x = self.conv2(x)
        x = self.relu(x)
        x = self.pool(x)
        x = self.flatten(x)
        x = self.fc(x)
        return x
```

Тренування — той самий патерн, що і в Уроці 04 (`DataLoader`, `Adam`, `CrossEntropyLoss`, `epoch → batch` цикл), тільки тепер на 60,000 реальних прикладах замість кількох точок. `CrossEntropyLoss` бере сирі logits (без ручного softmax) і цілі мітки класів напряму.

Оцінка — `argmax(dim=1)` дістає індекс класу з найбільшою ймовірністю з виходу мережі, порівнюється з реальною міткою:

```python
a = model(batch_x)
predicted = a.argmax(dim=1)
correct += (predicted == batch_y).sum().item()
accuracy = correct / len(test_data)
```

### Linear baseline — та сама схема, інша архітектура

```python
class LinearMLP(nn.Module):
    def __init__(self):
        super().__init__()
        self.fl = nn.Flatten()
        self.l1 = nn.Linear(784, 128)
        self.relu = torch.relu
        self.l2 = nn.Linear(128, 10)

    def forward(self, x):
        x = self.fl(x)
        x = self.l1(x)
        x = self.relu(x)
        x = self.l2(x)
        return x
```

Повністю без згорток — картинка одразу "розплющується" (`Flatten`) в 784 числа, і кожен з них має свою власну унікальну вагу.

### Результати

| Модель | Test Accuracy | Параметрів |
|---|---|---|
| CNN (2×conv) | **98.04–98.17%** | **5,258** |
| Linear MLP (baseline) | 96.63–97.09% | 101,770 |

CNN дала **вищу** точність з **майже в 19 разів меншою** кількістю параметрів.

### Чому саме так — weight sharing як практика, не тільки теорія

Kernel у CNN — це та сама вага, яка перевикористовується не тільки по всіх позиціях однієї картинки (Урок 05), а й по **всіх картинках датасету**: це один фізичний параметр у пам'яті, форвард якого викликається ідентично для кожного з 60,000 прикладів. Тому кожна вага CNN отримує градієнтний сигнал з тисяч точок (усі позиції × усі картинки), тоді як вага `Linear`, з'єднана з конкретним пікселем, отримує сигнал тільки з того, що відбувається саме в цьому пікселі — один раз на картинку.

Більше незалежних спостережень на одну вагу → стійкіша, менш шумна оцінка цієї ваги (той самий статистичний принцип, що й усереднення голосів дерев у Random Forest, тільки тут усереднюється градієнтний сигнал, не голосування). Тому мала кількість спільних ваг CNN узагальнює краще, ніж велика кількість вузькоспеціалізованих ваг Linear — менше overfitting, попри (а насправді *завдяки*) значно меншу кількість параметрів.

## Gotchas

- **`.unsqueeze(0)` для одного прикладу.** `train_data[0][0]` має shape `(1,28,28)` (канал, H, W) — без виміру `batch`. Для forward одного зображення явно додати `batch=1`: `.unsqueeze(0)` → `(1,1,28,28)`.
- **Пропущений крок у `forward` — типова, механічна, не концептуальна помилка.** Забути `relu` після `conv1` або другий `pool` перед `flatten` компілюється без помилки, просто дає неправильний shape або гіршу точність — звіряти `forward` рядок-за-рядком проти заздалегідь порахованого плану shape.
- **`lr` для Adam — той самий діапазон, що й раніше (Урок 04): `0.1` занадто високий, `0.001` працює.** Занадто високий `lr` на реальному датасеті виглядає як "модель не вчиться" чи навіть "зависла", а не як очевидна розбіжність.
- **Реальний датасет = реальний час.** 60,000 прикладів, `batch_size=64` → 938 батчів на епоху. Це відчутно повільніше за іграшкові приклади попередніх уроків на CPU — не баг, легітимний обсяг обчислень. Умова друку на кшталт `if epoch % 5 == 0` при малій кількості епох (наприклад 3) може приховати весь прогрес і створити хибне враження, що тренування зависло.
- **`sum(p.numel() for p in model.parameters())`** — це generator expression (як list comprehension з Фази 0, тільки без `[...]`), `p` тут — кожен параметр моделі (тензор ваг чи bias), `.numel()` рахує кількість чисел у ньому.
