# 07 — Регуляризація в Deep Learning: dropout, batch norm, early stopping

## Що це

Три інструменти боротьби з overfitting, специфічні для нейромереж (на відміну від L1/L2 з класичного ML, Фаза 2, Урок 08):

- **Dropout** — випадково "вимикає" частину нейронів шару під час тренування.
- **Batch Normalization** — нормалізує масштаб активацій усередині шару на кожному кроці.
- **Early stopping** — зупиняє тренування, коли модель перестає покращуватись на невидимих даних.

## Для чого

Overfitting у нейромережах виникає інакше, ніж у класичних моделях (немає прямого еквіваленту `.coef_`, який можна штрафувати L1/L2). Ці три інструменти працюють на різних рівнях: dropout — на рівні архітектури (заважає мережі покладатись на окремі нейрони), batch norm — на рівні стабільності самого процесу тренування, early stopping — на рівні контролю тривалості тренування.

## Розбір

### Dropout

`nn.Dropout(p=0.5)` — на кожному forward pass під час тренування випадково обнулює кожен нейрон шару з ймовірністю `p` (різний набір щоразу). Мережа не може розраховувати на конкретний нейрон — він може зникнути будь-якої миті, незалежно від того, наскільки він "хороший". Це змушує розподіляти інформацію надлишково по багатьох нейронах, а не концентрувати в одному крихкому шляху.

```python
self.dropout = torch.nn.Dropout(p=0.5)
# forward:
x = self.flatten(x)
x = self.dropout(x)   # на проміжних фічах, НЕ на фінальному виході перед loss
x = self.fc(x)
```

**Важливо, де ставити:** dropout на *фінальних* logits (прямо перед `criterion`) псує сигнал напряму — випадково обнулений logit правильного класу виглядає для loss як "модель не впевнена", хоча насправді впевнена. Dropout ставлять на проміжні (hidden) фічі, де справді є надлишковість.

Dropout працює **тільки** під час тренування. Під час оцінки всі нейрони мають бути активні — інакше кожен прогін дає інший випадковий результат. Перемикається через `model.train()` / `model.eval()`.

### Batch Normalization

`nn.BatchNorm2d(num_features)` — для кожного каналу окремо нормалізує активації в межах поточного батчу до середнього ≈0, std ≈1, потім застосовує два навчані параметри — `gamma` (масштаб) і `beta` (зсув), щоб мережа могла сама "відкотити" нормалізацію назад, якщо це вигідно.

```python
self.bn1 = torch.nn.BatchNorm2d(8)   # 8 = out_channels попереднього conv
# forward:
x = self.conv1(x)
x = self.bn1(x)
x = self.relu(x)
```

Без нормалізації вихідні значення різних шарів можуть бути на дуже різних масштабах — градієнтному спуску складно знайти один хороший `lr`, що годиться одразу для всіх шарів. BatchNorm тримає масштаб стабільним, тренування йде швидше і стабільніше.

**Параметрів додається `2 × num_features` на кожен шар** (`gamma`+`beta` по одному на канал) — наприклад `BatchNorm2d(8)` додає `16` параметрів, `BatchNorm2d(16)` — `32`.

**Клас vs виклик** (та сама механіка, що й з `nn.Conv2d`): кількість каналів передається при **створенні** об'єкта (`__init__`), не при виклику у `forward`. Кожен `BatchNorm` — окремий об'єкт для кожного шару з відповідною кількістю каналів, той самий патерн, що `conv1`/`conv2`.

### Early stopping

Стежить за loss на окремому **validation**-наборі (не train, не test) під час тренування. Якщо val loss не покращується `patience` епох поспіль — тренування зупиняється достроково.

**Чому не можна дивитись на `test_data` напряму:** рішення "коли зупинити тренування" — це фактично вибір фінальних ваг моделі. Якщо це рішення прийняте на основі test-даних, фінальна "test accuracy" вже не чесна оцінка — модель неявно підлаштована під test (той самий принцип data leakage, що і в Фазі 2, Урок 01). Тому виділяють окремий validation-набір з `train_data`, а `test_data` лишається недоторканим до фінальної оцінки:

```python
from torch.utils.data import random_split

train_subset, val_subset = random_split(train_data, [50000, 10000])
train_loader = DataLoader(train_subset, batch_size=64, shuffle=True)
val_loader = DataLoader(val_subset, batch_size=64, shuffle=False)
```

Логіка в тренувальному циклі:

```python
best_val_loss = float('inf')
patience_counter = 0

for epoch in range(15):
    for batch_x, batch_y in train_loader:
        optimizer.zero_grad()
        a = model(batch_x)
        L = criterion(a, batch_y)
        L.backward()
        optimizer.step()

    total_val_loss = 0
    for batch_x, batch_y in val_loader:
        a = model(batch_x)
        val_loss = criterion(a, batch_y)
        total_val_loss += val_loss.item()

    avg_val_loss = total_val_loss / len(val_loader)  # одне число на епоху

    if avg_val_loss < best_val_loss:
        best_val_loss = avg_val_loss
        patience_counter = 0
    else:
        patience_counter += 1

    if patience_counter >= 2:
        print("Early stopping!")
        break
```

**Ключова деталь:** порівняння `avg_val_loss` з `best_val_loss` відбувається **раз на епоху** (усереднений по всіх батчах val), не по кожному окремому батчу — окремий батч дає шумну, ненадійну оцінку.

## Результати (реальні числа)

| Конфігурація | Test Accuracy | Параметрів |
|---|---|---|
| CNN Урок 06 (без регуляризації) | 98.04-98.17% | 5,258 |
| + dropout + batch norm (3 епохи) | 98.31% | 5,306 |
| + dropout + batch norm + early stopping (до 15 епох, зупинився на 12-й) | **98.82%** | 5,306 |

Early stopping з довшим лімітом епох дав кращий результат, ніж фіксовані 3 епохи — модель мала змогу довчитись довше, а механізм зупинки убезпечив від зайвого тренування вже після точки, де це б шкодило.

## Gotchas

- **`nn.ReLU()`/`nn.Dropout()`/`nn.BatchNorm2d(n)` — це класи, потребують `()` для створення об'єкта.** `self.x = torch.nn.ReLU` (без дужок) зберігає сам клас, не інстанс — виклик `self.x(input)` не спрацює як очікується. Порівняти з `torch.relu` — це функція, викликається без попереднього створення об'єкта.
- **Dropout ставити на проміжні фічі, не на фінальний вихід перед loss.**
- **`model.eval()` обов'язковий перед оцінкою**, якщо є dropout/batchnorm у моделі — інакше dropout продовжує випадково обнуляти нейрони під час оцінки, результати будуть нестабільними між прогонами.
- **Early stopping monitors validation, не test.** Test лишається недоторканим до фінальної оцінки — інакше data leakage через вибір моменту зупинки.
- **Не кожен регуляризаційний інструмент дає ефект у кожному сценарії.** У маленькій CNN з weight sharing (Урок 06) dropout сам по собі майже не змінив результат — модель і без нього добре узагальнювала. Регуляризація найкорисніша саме там, де є реальний train-test розрив.
