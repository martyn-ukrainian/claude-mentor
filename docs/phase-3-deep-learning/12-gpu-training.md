# 12 — Робота з GPU: device-патерн і чому це 14× швидше

## Що це

Перенесення обчислень моделі з процесора (CPU) на графічний прискорювач (GPU). У PyTorch кожен тензор живе на конкретному **пристрої** (device), і все керується одним методом `.to(device)`. На Mac з Apple Silicon GPU доступний через бекенд **MPS** (Metal Performance Shaders), на NVIDIA — через **CUDA**; код однаковий, різниця лише в назві пристрою.

## Для чого

Нейромережа — це суцільні матричні множення, а матричне множення розпадається на тисячі **незалежних** дрібних обчислень: кожна клітинка результату рахується окремо, жодна не чекає іншу. GPU — це тисячі слабких ядер, які роблять їх одночасно; CPU — кілька потужних, які працюють по черзі. Наш замір тим самим скриптом (transfer learning з Уроку 11):

| Device | Секунд/епоха |
|---|---|
| CPU | ~13.9s |
| MPS (GPU того ж Mac) | **1.0s** |

~14× на крихітній задачі, де тренується лише голова. Що більша модель — то більший розрив: на реальних тренуваннях CPU не "повільніший", а практично непридатний. Саме тому "залізо" — повноправний член формули "архітектура + дані + тренування + залізо".

## Розбір

### Device-патерн — три рядки

```python
device = "mps" if torch.backends.mps.is_available() else "cpu"   # на NVIDIA: torch.cuda.is_available() → "cuda"

model = model.to(device)                                  # переїзд моделі (всіх ваг)

for batch_x, batch_y in train_loader:
    batch_x, batch_y = batch_x.to(device), batch_y.to(device)   # переїзд КОЖНОГО батча
    ...
```

**Головне правило: всі учасники обчислення — модель і кожен тензор — мають бути на одному пристрої.** Батчі переселяються у всіх циклах, де тензори входять у модель: train, val, test.

### Замір часу

```python
import time
for epoch in range(N_EPOCH):
    start = time.time()
    ...цикл батчів...
    print(f"Epoch {epoch}: {time.time() - start:.1f}s")
```

Перша GPU-епоха повільніша (у нас 5.2s проти 1.0s другої) — це **розігрів**: компіляція обчислень під GPU і холодні кеші. Справжню швидкість показує друга епоха і далі.

## Бонус: серія експериментів, яку GPU зробив можливою за один вечір

Кожен прогін — ~хвилина замість десяти на CPU, тому вдалося пройти повний діагностичний цикл:

| Конфігурація | Test accuracy | Висновок |
|---|---|---|
| 500 картинок, тільки голова (1 026 параметрів) | 78% | базлайн |
| 500 картинок, більше епох (16) | 78% | плато — епохи не важіль |
| 2000 картинок, тільки голова | 77% | дані не допомогли: вузьке місце — заморожені фічі (ResNet бачив справжні фото, а ми годуємо розтягнуті 32×32) |
| 2000 картинок + розморожений `layer4` (8.4M тренованих, param groups: fc `1e-3`, layer4 `1e-4`) | **89%** | дані і ємність розблокували одне одного |

Деталі фінального прогону: train loss впав до 0.0025 (модель вивчила 1600 картинок напам'ять — overfitting у прямому ефірі), але val був найкращий на епосі 1 — чекпойнт зберігся саме там, early stopping зупинив на 3-й, і test міряв **best-модель, не зазубрену фінальну**. Конвеєр з Уроку 11 (val split → чекпойнт → відновлення) реально врятував результат наступного ж дня після написання.

Мораль: 77 vs 78 — шум (2 картинки з 200 тестових); справжні важелі знаходяться діагностикою (епохи → плато → дані → плато → ємність/фічі), а не крутінням ручок навмання.

## Gotchas

- **`expected on mps but got cpu` — найчастіша GPU-помилка PyTorch.** Означає: хтось не переїхав. Знайти тензор/шар на CPU і додати `.to(device)`.
- **Порядок рядків: спершу зібрати модель, потім переселяти.** `model.to(device)` ДО `model.fc = nn.Linear(512, 2)` — і нова голова народжується на CPU при тілі на MPS → падіння на першому forward. Нові шари завжди створюються на CPU; переїзд — після останньої зміни архітектури.
- **Замір швидкості ≠ тренування хорошої моделі:** для порівняння досить 2 епох.
- **Чекпойнт, збережений з GPU-моделі,** при завантаженні на іншому пристрої може потребувати `torch.load(..., map_location=device)` — у межах однієї сесії на тому самому пристрої працює як є.
