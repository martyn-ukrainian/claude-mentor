# 04 — Оптимізатори (SGD/Adam), LR scheduling, batching

## Що це

Три практичні деталі тренувального циклу PyTorch, які роблять код ближчим до реального:

1. **Adam** — альтернатива `SGD`, збігається швидше в більшості випадків
2. **LR scheduling** — `learning rate`, що зменшується по ходу тренування, а не лишається сталим
3. **Batching** — тренування на пачках прикладів (`DataLoader`), а не на всьому датасеті чи по одному

## Для чого

`SGD` (Урок 03) — точна копія того, що ти виводив руками: `w -= lr*grad`. Працює, але на реальних задачах часто застрягає або збігається повільно. `Adam`, LR scheduling і batching — стандартні інструменти, які роблять тренування швидшим і стабільнішим, і які ти побачиш у майже будь-якому реальному PyTorch-коді.

## Розбір

### SGD vs Adam — чесне порівняння

`Adam` додає дві речі поверх звичайного градієнта: **momentum** (пам'ятає напрямок попередніх кроків, не смикається) і **адаптивний `lr`** (кожен параметр отримує свій ефективний крок, залежно від того, як шумно поводився його градієнт раніше).

Щоб чесно порівняти два оптимізатори — потрібно, щоб вони стартували з **однакових** випадкових ваг. `nn.Linear` ініціалізує ваги випадково при кожному створенні `model = Neuron()`, тому без фіксації випадковості два запуски непорівнювані (та сама проблема, що з CV в Фазі 2 Уроці 08 — один запуск не доказ):

```python
torch.manual_seed(42)
model = Neuron()
```

Результат (той самий старт `loss=0.00745` для обох):

| Ітерація | SGD | Adam |
|---|---|---|
| 0 | 0.00745 | 0.00745 |
| 10 | 0.0066 | 0.000114 |
| 40 | 0.0049 | 0.0000073 |

`SGD` майже не рухається (близько до мінімуму градієнт малий → крок малий, за тим самим правилом, що виводили в Уроці 01). `Adam` активно компенсує цю повільність — тому це типовий дефолтний вибір у реальному коді.

### LR scheduling — не завжди корисний наосліп

```python
scheduler = torch.optim.lr_scheduler.StepLR(optimizer, step_size=10, gamma=0.5)

for epoch in range(N):
    for batch_x, batch_y in loader:
        ...
        optimizer.step()
    scheduler.step()   # раз за епоху, ПІСЛЯ внутрішнього циклу
```

`StepLR` зменшує `lr` в `gamma` разів кожні `step_size` епох — велика ідея: далеко від мінімуму йти швидко, близько — обережно (не проскочити).

**Емпірична перевірка показала протилежний ефект тут:** з `step_size=10, gamma=0.5` на цій простій задачі `Adam` **застряг вище**, ніж без scheduler (`0.0000365` замість `0.0000073`) — бо `lr` зменшився занадто рано й агресивно для задачі, яка й так добре збігалась сама. Висновок: scheduling — це гіперпараметр, який треба підбирати під конкретну задачу, а не застосовувати наосліп як "завжди корисне".

### Batching — DataLoader і правильна структура циклу

```python
from torch.utils.data import TensorDataset, DataLoader

dataset = TensorDataset(X, y)
loader = DataLoader(dataset, batch_size=2, shuffle=True)

for epoch in range(N):          # зовнішній — повний прохід по всіх даних
    for batch_x, batch_y in loader:   # внутрішній — один батч
        optimizer.zero_grad()
        a = model(batch_x)
        L = criterion(a, batch_y)
        L.backward()
        optimizer.step()
    scheduler.step()
```

**Порядок вкладеності критичний:** `epoch` — зовні (скільки разів бачимо весь датасет), `batch` — всередині (скільки шматків датасету за один прохід). Переплутати легко — і це змінює саму суть тренування: `for batch → for epoch` (навпаки) означає "довбати один батч N разів, потім наступний" — зовсім не те, що "епоха".

`batch_size` визначає кількість батчів за епоху: `batch_size = розмір датасету` → 1 батч (full-batch, як без `DataLoader`); `batch_size = 1` → стохастичний GD (кожен приклад окремо); проміжне значення (mini-batch) — стандартний вибір.

### Чому взагалі потрібні батчі

Два окремі аргументи:
1. **Швидкість** — паралелізм GPU/CPU ефективніший на пачках прикладів, ніж по одному.
2. **Пам'ять** — реальні датасети (мільйони прикладів) фізично не влазять у пам'ять одночасно. Спроба `model(X)` на всьому датасеті одразу дала б `Out of Memory`. `batch_size` — компроміс між "по одному" (повільно) і "все одразу" (не влазить).

## Gotchas

- **Порівнювати оптимізатори/гіперпараметри без `torch.manual_seed()` — нечесно.** Випадкова ініціалізація ваг сама по собі дає різні стартові точки; без фіксованого seed різницю в числах легко приписати не тій причині.
- **Цільові значення мають бути в діапазоні, який модель фізично може видати.** Якщо вихід — `sigmoid` (завжди `(0,1)`), а `y=5.0` — модель ніколи не досягне нуля `loss`, скільки б не тренувалась.
- **`scheduler.step()` рахує власні виклики, не епохи напряму.** Якщо він всередині циклу по батчах — спрацьовує частіше, ніж `step_size` натякає (2 батчі на епоху → `step_size=10` фактично діє як `~5`).
- **`epoch`/`batch`-вкладеність легко переплутати місцями** — обидва варіанти синтаксично валідні, обидва запускаються без помилок, але дають зовсім різну поведінку тренування. Немає помилки, яка про це попередить — треба свідомо тримати "зовні = повний прохід, всередині = шматок" в голові.
