### ML на ринкових даних (trading) — сигнал, не автономний агент
_(2026-08-13, з розмови про "ML сам визначає найкращу стратегію")_ Вже висить у PROGRESS.md як "ML на власних даних (trading history)" — тут зафіксовані висновки обговорення, щоб не передумувати заново.

**Два рівні амбіції:**
- "ML сам торгує / сам знаходить стратегію" — це reinforcement learning (агент → дії купити/продати/тримати → винагорода прибуток/збиток). RL взагалі немає в 7-фазному ROADMAP — окрема спеціалізація після Фази 5. Не стартова точка.
- Реалістичний навчальний проєкт: **ML як один сигнал** — класифікація "ціна зросте/впаде за N періодів" (методологія Уроку 07-08 Фази 2: EDA → фічі → кореляції → модель → валідація), який живить власну ручну торгову логіку.

**Чому це важко саме на ринку (не інженерно, а статистично):**
1. **Нестаціонарність** — закономірності зникають, бо інші учасники теж адаптуються. Красивий backtest часто = підгонка під шум минулого, не реальний патерн.
2. **Multiple testing** — якщо прогнати купу факторів (FVG-заповнення, candle-патерни, десятки індикаторів) на кореляцію з ціною, щось "покорелює" випадково. На відміну від Telco (фічі мають бізнес-сенс апріорі) тут пошук патерну йде прямо в шумі. Тому: починати з **малої кількості апріорі обґрунтованих фіч**, не з "купи кореляцій".
3. **Часовий leakage, тонший ніж у Telco** — напр. "чи закрився 4h FVG" вимагає бачити майбутні свічки. Будь-яка фіча, що (навіть непрямо) використовує інформацію, недоступну на момент рішення → модель-"провидиця", що не працює наживо.
4. **Валідація** — не один train/test split і не звичайний CV, а **walk-forward**: тренуй на минулому, тестуй на невидимому майбутньому, зсувай вікно.

**Градація фіч за складністю добування:**
- **Volume** — легко з будь-якого API, стандартна фіча, гарний старт. Плюс: реальні дані про угоди, а не візуальна інтерпретація форми свічки (менше простору для multiple-testing самообману).
- **Market delta** (агресивні покупки vs продажі) — потребує tick-даних або спеціалізованого API, складніше дістати історично, але змістовна.
- **Стакан (order book, L2)** — найбагатше, але окрема ліга: tick-level дані, багато сховища, працює на секундних/хвилинних таймфреймах (територія HFT). Брати тільки якщо volume/delta-модель уже запрацювала. "Order book одразу — як почати Фазу 3 з transformers, минаючи перцептрон."

**Не зараз:** потребує впевненої Фази 2 + часових рядів. Коли братись — стартувати з volume/delta і walk-forward валідації.

## Цікаві теми для глибшого занурення

### Pipeline як наскрізний патерн — де ще він зустрічається
_(2026-08-09, питання виникло після Фази 2)_ Композиція обробників у ланцюг — один патерн, який у кожній фазі виглядає інакше, бо міняється одиниця даних:

| контекст | що виступає пайплайном | одиниця даних | навіщо він |
|---|---|---|---|
| Фаза 2, sklearn | `Pipeline` + `ColumnTransformer` | масив, одним махом | захист від data leakage у CV/GridSearch |
| Фаза 3, PyTorch | `nn.Sequential`, `forward()` | батч тензорів | композиція шарів |
| Фаза 4, LLM | RAG-ланцюг, агент із tool use (LangChain/LlamaIndex) | текст + виклики інструментів | оркестрація кроків міркування |
| Фаза 5, MLOps | FastAPI-сервіси, черги, CI/CD | HTTP-запит / подія | розділення на розгортувані одиниці |
| CV (у складі Фази 3) | `torchvision.transforms.v2.Compose`, Albumentations | картинка / тензор | аугментації й препроцесинг у фіксованому порядку |
| збоку: Pipecat | `Pipeline([transport.input(), stt, llm, tts, ...])` | кадр аудіо в реальному часі | конкурентність, low latency, переривання |

**Чому в CV `Compose`, а не `Pipeline`:** у трансформів немає `fit` — random crop і flip нічого не вивчають з даних, отже немає вивченого стану, отже немає ризику leakage, отже не потрібен захисний API. Але `v2.Normalize(mean=[0.485, 0.456, 0.406], std=[0.229, 0.224, 0.225])` — це той самий StandardScaler з Фази 2, просто константи пораховані одного разу по ImageNet, а не зафічені на моєму train. CV закрив ту саму проблему leakage **конвенцією замість API**.

**Чому detector → classifier пишуть руками, а не як `Compose`:** між стадіями міняється тип даних (картинка → бокси → кропи → мітки), а пайплайн-клас працює тільки коли в усіх ланок однаковий контракт входу/виходу. Так само влаштовані OCR (детекція тексту → розпізнавання), face recognition (детект → вирівнювання → embedding → пошук) і Faster R-CNN (RPN → ROI head, дві стадії всередині однієї моделі).

**Загальне правило, до якого все зводиться:** однаковий контракт у всіх ланок → фреймворк дає готовий клас (`Pipeline`, `Compose`, `nn.Sequential`, Pipecat із єдиним типом `Frame`). Різні типи між стадіями → просто пишеш код. Тому в типовому CV-проєкті пайплайнів три, на різних рівнях: дані (`Dataset → DataLoader → Compose`), модель (`nn.Sequential` шарів), інференс (detector → classifier, руками).

**Ключова відмінність sklearn vs Pipecat:** у sklearn контракт `fit`/`transform`, є фаза навчання, дані течуть тільки вперед, і головна цінність — **коректність** (структурно неможливо зробити leakage). У Pipecat контракт `async process_frame(frame, direction)`, фази навчання немає, є `UPSTREAM`-напрямок для переривань, і ланка може фільтрувати потік нічого не трансформуючи (як `MuteWhileBotSpeaking`) — головна цінність тут **конкурентність**.

Варте окремого копання, коли дійду до Фази 5: чим «пайплайн» у Airflow/Prefect (DAG, ретраї, розклад) відрізняється від обох, і коли лінійного ланцюга вже не вистачає.

## OHLCV time-series проект (ідея 16.08.2026, після Фази 3)

Навчити LSTM/Transformer на сирих OHLCV-числах (золото, EUR/USD, S&P500, BTC, GER30): свічка = вектор 5 фіч, послідовність = `(batch, seq, 5)` — прямий перенос Уроків 08-10.

**Чесна рамка (домовленість з ментором):** це навчальний проект, не торгова система. Головна мета — чесно виміряти модель проти наївного бейзлайна "завтра = сьогодні" (random walk), який на фінансових рядах розгромно сильний. Очікуваний результат "не побили бейзлайн" = успіх навчання, не провал. Технічні уроки: спліт строго по часу, нестаціонарність (сирі ціни → log-returns), нормалізація без підглядання в майбутнє, walk-forward валідація. Реалістичні цілі: класифікація режимів (тренд/флет), прогноз волатильності, аналіз власної торгової історії. Споріднено: agro-капстоун — теж time series, але з реальним фізичним сигналом.

**Уточнення скоупу (розмова 16-17.08, пізня ніч):** ідея студента "модель що знає всю історію + модель для тестування FVG" переформульована: модель ≠ база даних (ваги зберігають патерни, не записи — галюцинації замість цитат). Правильна архітектура: (1) справжня база OHLCV; (2) код-детектори патернів (FVG, order blocks — детерміновані правила, бектест без ML); (3) ML-суд: фічі з детекторів → таргет return через N свічок → логістична регресія/GB зі splitом по часу + feature_importances_ — "чи має патерн предиктивну силу vs бейзлайн"; (4) deep-модель тільки якщо в п.3 знайдеться сигнал. Фаза 2 інструментарій — головний герой. Misconception "модель = база даних" — у voice-чергу при нагоді (родич "заморожені=видалені": що саме живе у вагах).
